## Онбординг и понимание кода

```
Опиши архитектуру проекта: стек, точки входа, слои, основные потоки данных.
Не больше 20 строк. Код не меняй.
```

```
Проследи путь запроса POST /<endpoint> от роутера до БД. Для каждого шага: файл:строка и что происходит.
```

```
Почему <функция> реализована именно так? Посмотри git log -p и blame по этому файлу, найди PR/коммит с объяснением.
```

```
Я новичок в <технология>. Объясни @<файл> так, будто я знаю только <язык>. Отметь идиомы, которые стоит запомнить.
```

## Планирование

```
[plan mode] Мне нужно <задача>. Изучи релевантный код и предложи 2–3 варианта реализации
с плюсами/минусами и оценкой риска. Рекомендуй один. Код не пиши.
```

```
Разбей <большую задачу> на шаги, каждый из которых можно закоммитить отдельно и который
оставляет проект в рабочем состоянии. Сохрани план в docs/plans/<имя>.md с чекбоксами.
```

```
Прочитай docs/plans/<имя>.md, выполни следующий невыполненный шаг, отметь его и остановись.
```

## Баги и отладка

```
Ошибка: <текст/стектрейс>. Шаги воспроизведения: <...>.
Сначала воспроизведи, затем сформулируй 2–3 гипотезы и проверь их по очереди.
Исправляй первопричину, а не симптом. В конце — тест, который ловит этот баг.
```

```
Тест <имя> падает нестабильно (flaky). Запусти его 20 раз, найди причину нестабильности
(время, порядок, общее состояние, сеть) и исправь, не ослабляя проверки.
```

```
Сравни поведение на ветке main и на текущей: найди коммит, который сломал <поведение>
(используй git bisect, тест-критерий: <команда>).
```

## Тесты

```
Напиши тесты для @<файл> в стиле соседних тестов. Сначала перечисли сценарии
(happy path, границы, ошибки), потом код. Если найдёшь баг — не подгоняй тест, сообщи.
```

```
TDD: по этой спецификации <...> напиши только тесты, запусти, убедись, что они падают, закоммить.
Реализацию не трогай.
```

```
Какие ветки кода в @<файл> не покрыты тестами? Добавь тесты только для рискованных мест.
```

## Рефакторинг

```
Отрефактори @<файл>: <цель — например, разделить на модули / убрать дублирование>.
Поведение не меняй. Перед началом убедись, что тесты зелёные, после — что тоже зелёные.
Делай маленькими шагами, по коммиту на шаг.
```

```
Найди все места, где используется <старый API>. Верни список файл:строка.
Потом мигрируй на <новый API> по одному файлу, запуская тесты после каждого.
```

```
Переименуй <сущность> в <новое имя> везде: код, тесты, документация, конфиги, строки в логах.
Проверь grep-ом, что старое имя не осталось.
```

## Ревью и качество

```
Сделай ревью `git diff main...HEAD` как строгий senior: баги, граничные случаи, безопасность,
тесты, читаемость. Формат: 🔴/🟡/🟢, файл:строка, проблема → исправление. Не придумывай проблем.
```

```
Посмотри этот код глазами человека, который будет поддерживать его через год.
Что будет непонятно? Что сломается первым?
```

## Git и PR

```
Разбей текущие незакоммиченные изменения на логические коммиты в формате Conventional Commits.
Покажи план разбиения, потом выполни.
```

```
Создай PR: заголовок, что и зачем изменено, как тестировать (чек-лист), риски.
Используй gh pr create. Не пушь, пока я не подтвержу.
```

```
Реши конфликты мерджа. Для каждого конфликта объясни, что было в обеих ветках и почему выбрано такое решение.
```

## Фронтенд и UI

```
Сверстай компонент по макету [изображение]. Используй существующие компоненты из src/components/ui.
После — открой в браузере, сделай скриншот, сравни с макетом, исправь расхождения (2–3 итерации).
```

```
Проверь страницу <url> на доступность (a11y): контраст, alt, фокус, aria, навигация с клавиатуры. Исправь найденное.
```

## Данные и БД

```
Напиши миграцию для <изменение схемы>. Она должна быть обратимой и безопасной на большой таблице
(без долгих блокировок). Объясни план выката.
```

```
Этот запрос медленный: <SQL>. Посмотри EXPLAIN (через MCP к БД, read-only), предложи индексы или переписывание.
```

## Документация

```
Обнови README по фактическому состоянию проекта: установка, запуск, тесты, переменные окружения.
Проверь каждую команду запуском.
```

```
Напиши ADR (Architecture Decision Record) по решению <...>: контекст, варианты, решение, последствия.
```

## Производительность

```
Профилируй <сценарий>. Найди топ-3 узких места с цифрами до/после. Не оптимизируй без замеров.
```

## Безопасность

```
Проверь <модуль> по OWASP Top 10. Для каждой находки: риск, сценарий эксплуатации в 1 строку,
исправление. Ищи также секреты в коде и истории git.
```

## Мета: управление самим Claude

```
Стоп. Прежде чем продолжать, объясни, что ты собираешься сделать и почему.
```

```
Ты уже дважды пробовал этот подход. Сделай шаг назад: какие у нас есть факты,
какие гипотезы отброшены, что ещё не проверяли?
```

```
Проанализируй эту сессию: какие правила стоит добавить в CLAUDE.md, чтобы в следующий раз
ты не делал тех же ошибок? Предложи изменения, не применяй.
```

```
Обнови docs/plans/<имя>.md: что сделано, какие решения приняты, что дальше, открытые вопросы.
(перед /clear — чтобы продолжить в новой сессии)
```
